# Exercise 05: Investigate a DNS or TLS failure

> **Simulated lab failure.** Every hostname, IP address, command, and output
> below comes from the assignment's supplied simulation. None of it is a
> result from my real domain, and I did not run these commands.

## Setting and prediction

I will be using the supplied simulation for the assignment.

The failed check is these two commands:

```
dig site.lab.example A +noall +answer
curl -Iv https://site.lab.example/
```

The first command is providing the DNS A record, which is stored on Cloudflare
and points to the VM on Azure. The second command is sending a request to the
website using curl.

**Prediction:** If it were set up correctly for Railway, the record would be
CNAME and not A. The A record is pointing to the IP address connected to the
VM on Azure whereas CNAME will point to current-app.up.railway.app. The
certificate name would be site.lab.example and the page would load.

## Failed check and evidence

Simulated output, supplied by the assignment:

```
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  A  198.51.100.24

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (198.51.100.24) port 443
* Server certificate: subject: CN=old-vm.lab.example
* SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name
```

The first check showed the certificate name as old-vm.lab.example when it
should match the target host name which is site.lab.example.

## Diagnosis

**DNS to the destination:** The output shows the IP address 198.51.100.24
which is the IP address of the old Azure VM.

**TLS to the certificate:** Because curl connected to the old VM, it got the
old VM's certificate, old-vm.lab.example. The problem is the traffic is going
to the wrong server. The DNS sending traffic to the old VM is the first issue
and it is what causes the certificate name not to match.

**Proposed repair:** In Cloudflare,replace the old A record with a CNAME that points to current-app.up.railway.app.

**What remains uncertain:** After changing the DNS record, you would still need
to confirm that the certificate is working and reaching the correct server and
check the site to ensure database changes are displayed on the front end.

## Repair and repeated check

I interpreted the supplied follow-up output and did not run it.

Simulated follow-up output, supplied by the assignment:

```
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  CNAME  current-app.up.railway.app.
current-app.up.railway.app.  300  IN  A  203.0.113.44

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (203.0.113.44) port 443
* Server certificate: subject: CN=site.lab.example
* SSL certificate verify ok.
< HTTP/2 200
```

**Record change:** It shows the record changed from A to CNAME and it now
points to the correct server, current-app.up.railway.app, which has the IP
203.0.113.44.

**Repeated check:** The site now connects to the correct IP address which is
the server on Railway and not the old one hosted on Azure. The result proved
successful with no error message and showed the correct certificate name as
site.lab.example.

**Compared with my initial proposal:** Yes, it does support my original
diagnosis. It looks as though the record was changed like we did last class
when switching to Railway from the Azure VM. The record is now CNAME and points
to current-app.up.railway.app, which has the IP address of the current app on
Railway, when before the A record pointed to the VM on Azure. Now that we are
directed at the correct server, there is no longer an error.

## What you learned

To tell a DNS problem apart from a TLS problem, you can compare the Railway
provided URL against the site.lab.example URL. Railway skips the DNS but if I
were to look up the site itself, I don't skip over the DNS. Therefore, I would
not be able to reach the site by typing it into the address bar but could via
Railway's URL if it were a DNS problem. A DNS problem will only break the
site.lab.example URL but a problem with the app will break both that URL and
the Railway URL.
